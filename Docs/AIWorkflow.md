# AI-Assisted Engineering 프로세스 및 품질 통제

이 문서는 Eye of the Storm 개발 과정에서 Claude를 적용한 범위, 코드 품질과 정확성을 통제하기 위해 구축한 파이프라인, 그리고 AI가 생성한 설계와 추론을 검증해 교정한 사례를 정리한 문서입니다.

## 역할 분담 및 경계

| 영역 | 구현 주체 | 직접 수행한 엔지니어링 범위 |
| --- | --- | --- |
| 날씨 렌더링 플러그인 (`Plugins/VW`) | 직접 구현 (UE5 RDG API 참조와 이식 절차 정리에 Claude 활용) | 원본 Vulkan 렌더러 제작, UE5 이식 코드 작성, 화면 결과 검증, 아키텍처 판단, GPU 성능 측정 |
| 게임 모듈 (`Source/EyeOfTheStorm`) | AI 페어 프로그래밍 (달리기, 카메라 줌, 슬로 모션 노티파이, 돌진 옵션은 직접 작성) | 시스템 설계, 코드 규약 수립, 코드 리뷰, 플레이 검증 및 밸런스 튜닝 |
| 에디터 자동화 스크립트 (`Tools`) | 요구사항 정의 및 조회 파이프라인 설계(직접), UE Python 구현(Claude) | 바이너리 에셋 직렬화 조회 구조 설계, 출력 결과 검증 |
| 레벨과 에셋 | 공동 작업 | 공간 배치 판단, 캐릭터와 에셋 준비, 연출 검증 |

역할 경계는 디버깅 소유권과 검증 비용을 기준으로 설정했습니다. 렌더링 파이프라인은 수학적 모델과 GPU 패스 상태를 직접 이해해야 결함을 추적할 수 있으므로 전체 구현을 직접 수행했습니다. 게임플레이 모듈과 에디터 도구는 코드 리뷰와 실행 결과로 정합성을 빠르게 검증할 수 있어 AI 페어 프로그래밍을 적극 활용하고 아키텍처 통제와 검증에 집중했습니다.

## 품질 통제 파이프라인

AI 생성 코드의 일관성을 유지하고 추측에 기반한 오류를 차단하기 위해 세 가지 통제 장치를 운용했습니다.

- **코드 규약 및 아키텍처 기준 선행 정의**: 헤더 파일의 접근 지정자 및 멤버 선언 순서, UHT가 에디터 툴팁으로 수집하는 주석 위치(프로퍼티 바로 윗줄에만 작성), 커밋 메시지 형식을 사전에 명문화하고 기준 코드를 직접 작성해 공유했습니다. 이를 통해 AI가 생성한 코드와 직접 작성한 코드의 구조적 일관성을 유지했습니다.
- **컨텍스트 그라운딩 자동화**: 바이너리 `.uasset` 파일에 대한 AI의 추측(환각)을 구조적으로 차단하기 위해 두 가지 직접 조회 경로를 구축했습니다. UE Python 기반 에셋 덤프 스크립트(`Tools/ue_dump.py`, `Tools/ue.py`)로 에셋과 블루프린트의 직렬화 데이터(T3D)와 클래스 기본값(CDO)을 텍스트로 추출해 읽도록 했고, UE 5.7 환경에 맞게 수정한 MCP 서버(UnrealMCP) 파이프라인을 연결해 실행 중인 에디터 상태를 직접 조회하게 했습니다.
- **증거 기반 검증**: 렌더링 결함과 프레임 이상은 AI의 초기 가설을 곧바로 코드 수정으로 연결하지 않았습니다. 프레임 캡처, GPU 덤프(`DumpGPU`), 콘솔 명령을 통한 렌더링 기능 분리 테스트로 관측 증거를 먼저 확보한 뒤 원인을 좁혀 수정했습니다.

## AI 생성 설계와 추론의 검증 및 교정 사례

### 도구 제약으로 인한 UI 아키텍처 왜곡 방지

- **이슈 및 AI 초기 제안**: 체력바 UI 구현을 위임했을 때, 연동된 자동화 도구(UnrealMCP, UE Python)로 위젯 블루프린트 레이아웃을 편집할 수 없자 AI가 위젯 배치까지 C++ 코드로 구성하는 방향으로 설계를 변경했습니다.
- **검증 방식**: 프로젝트의 역할 분리 기준(게임 로직은 C++, 데이터와 UI 레이아웃 연출은 블루프린트)과 추후 레이아웃 수정 시 발생하는 유지보수 비용을 검토했습니다.
- **엔지니어링 의사결정 및 수정**: 도구 제약 때문에 아키텍처 경계가 무너지는 것을 방지하기 위해 C++ 레이아웃 구성을 반려하고 롤백했습니다. 체력 이벤트 처리와 잔상 바 갱신 로직만 C++로 유지하고, 위젯 배치는 위젯 블루프린트로 분리해 직접 구성했습니다. ([0e58ce6](https://github.com/Shell4026/EyeOfTheStorm/commit/0e58ce6))

### GPU 덤프와 대조 실험을 통한 렌더링 버그 원인 특정

- **이슈 및 AI 초기 제안**: 체적 그림자(빛줄기) 패스를 이식한 뒤 빛줄기가 출력되지 않거나 극도로 약하게 표시되는 문제가 발생했습니다. 1차 수정 이후에도 증상이 남았을 때 AI는 캡처 범위 부족과 자동 노출 영향이라는 두 가지 가설을 제시했습니다.
- **검증 방식**: GPU 덤프(`DumpGPU`)로 태양 깊이 맵(`VW.ShadowDepth`) 전체 픽셀이 동일한 원평면 값으로 채워진 것을 먼저 확인했습니다. 이후 자동 노출을 비활성화한 대조 실험에서 시간 파라미터를 드래그하는 프레임에만 빛줄기가 보이고 정지 상태에서는 대기 원근까지 약해지는 현상을 관측해, 정적 LUT 갱신과 바인딩 경로로 범위를 좁혔습니다.
- **엔지니어링 의사결정 및 수정**: 엔진 소스(`BuildOrthoMatrix`)에서 직교 SceneCapture의 원평면이 약 2.6km로 고정되어 있음을 확인하고, 커스텀 직교 투영 행렬을 적용해 캡처 거리 10km, 원평면 20km로 확장했습니다. 또한 이전 리뷰에서 셰이더 코드만 대조하느라 놓쳤던 C++ 리소스 바인딩 오류(Multiple Scattering LUT 슬롯에 Transmittance LUT 바인딩)를 찾아 수정했습니다. ([120fa63](https://github.com/Shell4026/EyeOfTheStorm/commit/120fa63), [기술 문서](TechnicalDesign.md#태양-깊이-캡처-범위))

### 프레임 캡처 기반 틱 순서 버그 원인 확정

- **이슈 및 AI 초기 제안**: 연속 구르기 입력 시 화면이 한 프레임 깜빡이며 튀는 현상에 대해 AI가 카메라 회전 문제가 아닌 모션 블러 현상으로 추정했습니다.
- **검증 방식**: 콘솔 명령으로 모션 블러와 TSR을 비활성화해 후처리 영향을 배제한 뒤, 문제가 발생하는 순간의 연속 프레임을 캡처해 가운데 한 프레임에서만 카메라 방향이 회전하는 증거를 확보했습니다.
- **엔지니어링 의사결정 및 수정**: 확보한 프레임 증거를 토대로 엔진 월드 틱 순서(틱 그룹, 타이머, 카메라 갱신)를 추적해 원인을 확정했습니다. 타이머에서 실행된 버퍼 회피가 스프링 암 틱 이후 캐릭터를 180도 회전시키며 카메라가 함께 돌아간 것이 원인이었으며, 스프링 암이 캐릭터 회전을 상속받지 않도록 수정해 해결했습니다. ([ef46e56](https://github.com/Shell4026/EyeOfTheStorm/commit/ef46e56), [기술 문서](TechnicalDesign.md#연속-구르기-때-한-프레임-카메라가-튐))

### 증상 범위 분리를 통한 구름 재투영 히스토리 결함 해결

- **이슈 및 AI 초기 제안**: 보스가 하늘 앞에서 움직일 때 윤곽을 따라 하늘색 잔상이 남는 현상에 대해 AI는 엔진의 모션 블러나 TSR 잔상을 원인으로 추정했습니다.
- **검증 방식**: 잔상의 형태가 구름이 빠지고 하늘색만 노출되는 윤곽이라는 점에 착안해 엔진 후처리가 아닌 커스텀 구름 시간적 재투영(Temporal Reprojection) 패스 결함으로 범위를 분리하고, 원본 셰이더의 히스토리 누적 식을 대조했습니다.
- **엔지니어링 의사결정 및 수정**: 원본 렌더러에는 하늘 앞을 가로지르는 동적 물체가 없어 드러나지 않았던 결함(구름 없음 상태의 무효 히스토리를 유효 샘플 1개로 누적 계산)을 확인하고, 무효 히스토리를 누적 가중치에서 제외하도록 수정했습니다. ([7ad7f26](https://github.com/Shell4026/EyeOfTheStorm/commit/7ad7f26), [기술 문서](TechnicalDesign.md#재투영-히스토리-가중치))

### 바이너리 파싱과 임포터 대조를 통한 엔진 버그 규명

- **이슈 및 AI 초기 제안**: 자체 제작 캐릭터의 모든 모프 타깃이 가중치 1에서 얼굴 크기를 축소시키는 문제에 대해 AI는 블렌더 측 메시 스케일 미적용을 원인으로 추정했습니다.
- **검증 방식**: 블렌더 메시 스케일이 1임을 확인해 초기 가설을 배제한 뒤, 검증 계층을 블렌더, FBX 파일, 언리얼 임포터로 분리했습니다. Python으로 FBX 바이너리를 직접 파싱해 셰이프 키 137개의 델타 값이 정상임을 검증했고, 레거시 FBX 임포터로 임포트했을 때 정상 동작함을 대조해 UE 5.7 Interchange 임포터로 원인을 특정한 뒤 엔진 소스에서 동작 근거를 확인했습니다.
- **엔지니어링 의사결정 및 수정**: Interchange가 시간 0 포즈를 바인드 포즈로 사용할 때 기본 메시만 재스키닝하고 모프 타깃은 갱신하지 않아 머리 본의 1.05배 스케일이 모든 모프에 역반영되는 엔진 동작을 규명했습니다. 캐릭터 비율은 유지하되 블렌더의 포즈 스케일을 제거하고 애니메이션 블루프린트에서 머리 스케일을 재적용하는 파이프라인으로 해결했습니다. ([기술 문서](TechnicalDesign.md#모프-타깃이-얼굴을-줄임))

### 책임 분리를 위한 컴포넌트 구조 리팩터링

- **이슈 및 AI 초기 제안**: 초기 구현에서는 보스 클래스 내부에 체력 변화에 따른 날씨 전환 로직이 결합되어 있어, 날씨 연출이 필요 없는 액터와 역할을 분리하기 어려운 구조였습니다.
- **검증 방식**: 보스 클래스 내부 날씨 제어 코드의 의존성을 점검한 결과, 체력 컴포넌트와 날씨 서브시스템만 참조하고 있어 분리 경계가 명확함을 확인했습니다.
- **엔지니어링 의사결정 및 수정**: 체력 연동 날씨 제어를 독립 컴포넌트(`UStormHealthWeatherComponent`)로 분리하고, 보스 전용이 아니라 체력 컴포넌트를 보유한 모든 액터에 부착할 수 있도록 일반화했습니다. 분리 과정에서 컴포넌트 간 `BeginPlay` 호출 순서 비보장으로 초기 날씨가 잘못 적용될 수 있는 잠재 결함도 함께 차단했습니다. ([0cbb072](https://github.com/Shell4026/EyeOfTheStorm/commit/0cbb072), [기술 문서](TechnicalDesign.md#체력-날씨-컴포넌트))
